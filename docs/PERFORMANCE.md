# QuizSpark 3.1 — ผลทดสอบ 200 ผู้เล่น

ทดสอบเมื่อ 23 กันยายน 2026 ด้วย HTTP/WebSocket จริง แยก process ของ server
และเครื่องมือสร้างโหลด แต่รันอยู่บนเครื่องทดสอบเดียวกันผ่าน loopback
ผลนี้ยังไม่รวม NGINX/TLS/อินเทอร์เน็ต/Wi-Fi ของระบบที่ deploy

## ผลที่วัดได้

ทุกกรณีมีผู้เล่น 200 คนและผู้จัดอีก 1 connection เปิด permessage-deflate
โจทย์สลับ MCQ กับพิมพ์คำตอบ เวลาข้อละ 20 วินาที รอ 1 วินาทีหลังทุกคนได้รับโจทย์
แล้วเริ่มส่งคำตอบ ผู้เล่นทุกคนเข้าห้องสำเร็จ 200/200

| รุ่น / รูปแบบ | จำนวนข้อ | คำตอบรับสำเร็จต่อข้อ | ack p95 ต่อข้อ | หลุด |
|---|---:|---|---|---:|
| 3.0 เดิม ตอบพร้อมกัน | 2 | 169/200, 158/200 | 18,084.80–18,128.24 ms | 0 |
| 3.1 ตอบพร้อมกัน | 5 | 200/200 ทุกข้อ | 109.90–132.12 ms | 0 |
| 3.1 ทยอยตอบภายใน 10 วินาที | 3 | 200/200 ทุกข้อ | 2.15–2.57 ms | 0 |
| 3.1 เข้าห้องพร้อมกัน และตอบพร้อมกัน | 5 | 200/200 ทุกข้อ | 106.90–142.75 ms | 0 |

3.0 ได้ `round_closed` 31 และ 42 ครั้งในสองข้อ ส่วน 3.1 ไม่มี answer errors
และ cleanup สำเร็จทุกกรณี รวมคำตอบ 2,600/2,600 ใน 13 ข้อของรุ่น 3.1

เปรียบเทียบข้อมูลที่ผู้ทดสอบได้รับในช่วงตอบจนถึงเฉลย:

| รุ่น / รูปแบบ | ข้อความต่อข้อ | JSON หลังคลาย compression ต่อข้อ |
|---|---:|---:|
| 3.0 ตอบพร้อมกัน | 32,001–34,201 | 1,048.59–1,111.13 MiB |
| 3.1 ตอบพร้อมกัน | 400 | 11.26–11.41 MiB |

ตัวเลข JSON ไม่ใช่ bandwidth บนสายเครือข่าย ค่า p95 คำนวณเฉพาะคำตอบที่มี
acknowledgement จึงต้องอ่านจำนวนคำตอบที่ตกหล่นควบคู่กัน รุ่นเดิมมีจำนวนข้อ
ทดสอบน้อยกว่าเพราะแต่ละข้อรอจนหมดเวลา; ไม่มีการนำ percentile หลายข้อมารวมเฉลี่ย

## แก้ส่วนใด

- หลังรับคำตอบ ส่งสถานะยืนยันกลับเฉพาะผู้ตอบ ใช้ protocol `state` เดิม
  เพื่อให้ UI และสคริปต์ stress test เดิมยังทำงาน
- รวมจำนวนคำตอบบนหน้าผู้จัดแล้วส่งได้สูงสุดทุก 200 ms
  ส่งสถานะครบทุกคนทันทีเมื่อเริ่มข้อ เฉลย แสดงอันดับ หรือปิดห้อง
- การเข้าห้องและสถานะ online รวมเป็นรอบ 200 ms ผู้ที่เพิ่งเชื่อมต่อได้ snapshot ทันที
- แต่ละ WebSocket มี writer และคิวของตนเอง จำกัด 32 รายการ
  รวม snapshot ที่ต่อกันของข้อ/ช่วงเกมเดียวกัน แต่รักษาลำดับการเปลี่ยนช่วงเกม
  การส่งที่ค้างเกิน 3 วินาทีหรือคิวเต็มจะปิดเฉพาะ connection นั้นให้ reconnect
- ส่วนที่ถือ `room.lock` ไม่มีการรอ network I/O จึงไม่ให้ผู้เล่นที่รับช้าขวางการรับคำตอบ
- คำนวณ ranking ครั้งเดียวต่อ broadcast และ serialize ส่วนที่เหมือนกันครั้งเดียว
- ใช้เวลา monotonic ขณะที่ handler ได้รับข้อความ ก่อนรอ room lock คำนวณคะแนน
  ไม่เชื่อเวลาที่ client ส่งมา และยังบังคับ deadline/รับคำตอบได้ครั้งเดียวเหมือนเดิม

## สภาพทดสอบและไฟล์ผล

- Python 3.12.14, aiohttp 3.13.5, Pillow 12.3.0
- Linux; CPU quota 8 cores, memory limit 14 GiB ในสภาพทดสอบ
- ใช้ Python server 1 process; generator อีก 1 process ไม่มี Docker daemon ในสภาพนี้
- ทดสอบทีละ workload โดยเริ่ม server ชั่วคราวใหม่ เพื่อไม่ให้ quota การเปิด connection
  จากกรณีก่อนหน้าปะปนกับผลถัดไป ไม่มีการแก้หรือปิด rate limit ในแอป
- ตัวสร้างโหลดวัด event-loop lag ของตัวเองด้วย เพราะ latency รวมการอ่านฝั่ง client

ผลดิบ:

- `load-results/baseline-burst-200.json`
- `load-results/burst-200.json`
- `load-results/spread-200.json`
- `load-results/join-burst-200.json`

pip install -r requirements.txt

## ก่อนใช้กับผู้เรียน 200 คน

ทดสอบผ่าน URL จริงจากอีกเครื่องด้วย `tools/stress_test.py`
เป้าหมายเริ่มต้นคือคำตอบครบ 200/200 ทุกข้อ, ack p95 ≤ 1 วินาที,
ไม่มี answer errors และไม่มี connection หลุด ค่านี้เป็นเกณฑ์เสนอ ไม่ใช่ SLA
ทดสอบหลายข้อทั้งแบบพร้อมกันและทยอยตอบ รวมถึงอุปกรณ์และ Wi-Fi ที่ใช้จริง

CPU/RAM ว่างอย่างเดียวไม่รับรองผลของเครือข่ายหรือ latency ข้อสอบที่มีรูป
และการอัปโหลดไฟล์พร้อมกับเล่นไม่ได้รวมอยู่ใน workload ข้างต้น

ระบบยังใช้ 1 process/1 replica และเก็บห้องเกมใน RAM การเพิ่ม workers หรือ replicas
โดยไม่เปลี่ยนการจัดเก็บห้องเกมจะทำให้ connection ของห้องเดียวกันแยกกัน
การทดสอบนี้ยืนยันหนึ่งห้อง 200 คน ไม่ได้วัดหลายห้องเต็มพร้อมกัน

Connection/join limit ยังคง 300 ครั้ง/IP/60 วินาที หลัง reverse proxy อาจเห็นผู้เล่น
ทั้งหมดเป็น IP เดียว จึงมีผลต่อการ reconnect พร้อมกันจำนวนมากภายในนาทีเดียว
รันชุดทดสอบซ้ำให้เว้นอย่างน้อย 65 วินาที และแยก HTTP 429/`rate_limit` จากผลประมวลผล
